# tOS — Core Architecture Boundaries

状態：B-03としてHuman Review承認済み（[PR #8](https://github.com/tanakakeisuke-github/tOS/pull/8)）。実装済みの構成やtOS v0.1全体の確定範囲を示すものではない。具体化と依存の方向の表記修正は[PR #28](https://github.com/tanakakeisuke-github/tOS/pull/28)で承認・main反映済み。

目的と保持する知識は[Purpose](PURPOSE.md)、判断原則とHuman Gateは[Constitution](../CONSTITUTION.md)を参照する。本書はそれらを繰り返さず、媒体をまたぐ境界と交換点を定める案である。

## 三層の責務と受け渡し

| 層 | 責務 | 入るもの | 出るもの |
|---|---|---|---|
| **tOS Core** | 媒体に依存しない制作の共通枠組み。目的・制約を持つ仕事の分割と引き継ぎ、判断と根拠の記録、Reviewと人間の承認点、結果と学びの区別を扱う。 | 適用するtOSの版、仕事の目的・範囲・入力・受入条件、担当と承認状態、作業結果・検証根拠。 | 次の担当者が読める仕事と知識の記録、Reviewに渡す成果と根拠、人間の判断を待つ状態、改善候補。 |
| **Studio Template** | Coreの共通枠組みを媒体の制作へ具体化する。専門Role、成果物、制作段階、品質評価と媒体固有の引き継ぎを定める。 | 適用するCoreの版・共通枠組み、媒体の制作知識と評価観点。 | Templateの版、媒体固有のRole・成果物・Workflow・評価観点をProjectが選べる形にしたもの。 |
| **Project** | 一つの作品・製品について目的、体験、制約、優先順位、制作範囲と完成判断を具体化し、作業を進める。 | 選んだCoreとTemplateの版、作品の目的・制約、制作上の判断と素材。 | 作品の成果物、個々の仕事の結果・評価・判断履歴、Projectの学びとtOSへの改善提案。 |

共通の枠組みを具体化する方向は **tOS Core → Studio Template → Project**。規則を参照する依存方向は **Project → Studio Template → tOS Core**。ProjectはTemplateの媒体上の約束に加え、Coreの共通の仕事・知識・承認の約束も直接使う。TemplateはCoreの共通枠組みを使う。Coreは特定のTemplate、Project、作品内容、媒体の制作段階に依存しない。Projectから得た学びをCoreへ戻す場合も、提案・評価・人間の判断を経て次版を検討し、進行中のCoreを暗黙に書き換えない。

Coreの最小境界は「仕事と知識を版・出所・判断状態とともに渡し、ReviewとHuman Gateへ接続できること」までとする設計案である。保存形式、権限モデル、状態名、実行手順、具体的なToolは後続設計で定める。

## 実行技術との交換点

Runtime / Orchestrator / Vendorは三層とは別の実行技術の選択肢であり、Coreの責務そのものを所有しない。交換時に保ちたいのは、特定製品のAPIではなく、次の概念上の受け渡しである。

| 交換箇所 | 受け渡しで保つ契約 | 交換してよい部分 |
|---|---|---|
| **Runtime**（担当が仕事を実行する環境） | 承認された仕事の目的・範囲・入力・制約を受け取り、成果、実際に行った検証、未解決事項を出所とともに返す。人間の着手・完了承認を実行結果で代替しない。 | 実行場所、利用可能なTool、AI等の実行方式。 |
| **Orchestrator**（仕事の受け渡しを調整する仕組み） | 仕事の依存、担当、引き継ぎ、Review、人間の判断待ちを見失わず、判断を要する箇所で停止できる。 | 調整方法、通知方法、作業の順序づけや自動化の方式。 |
| **Vendor**（外部の能力・サービスの提供元） | 利用する能力と制約、入力した情報、得た出力とその出所を識別でき、判断・記録を特定提供元だけに閉じ込めない。 | モデル、サービス、提供事業者とその接続方法。 |

この表は交換可能性の**設計条件**であり、無改修で交換できるという検証結果ではない。具体的なAPI、データ形式、製品、運用構成、同等性の判定方法はここで選ばない。Role / Actor / Agent / Modelの厳密な関係も後続の担当範囲である。

## Project Bootstrapの位置

[Future Vision](../vision/FUTURE_VISION.md)にあるProject Bootstrapは、Coreの版、Studio Templateの版、Project固有の目的・制約から、制作開始に必要な知識と仕事の入口を用意する**将来構想**である。三層の境界をまたぐ入口として位置づけるが、本書は入力項目、生成物、手動・自動の分担や承認手順を確定しない。現在のBootstrap Knowledgeの保存を、この機能の実装と扱わない。

## 二つの媒体で境界を確かめる

| 例 | Coreで共通に扱うもの | Templateで決めるもの | Projectで決めるもの |
|---|---|---|---|
| **Game** | 仕事の範囲・引き継ぎ、検証根拠、Reviewと人間の判断。 | 例えばPrototype → Vertical Slice → Alpha → Beta → Release Candidateという段階、Playtestやゲーム体験の評価観点、専門Roleと成果物。 | 個別ゲームの体験目標、対応機種、遊びの制約、今回のPrototype範囲と評価結果。 |
| **Film** | 同じ仕事・知識・判断の枠組み。 | 例えば脚本、撮影、編集、試写に沿った段階と映像・音声の評価観点、専門Roleと成果物。 | 個別作品の物語、尺、予算・撮影制約、試写結果と公開判断。 |

Gameの段階をFilmへ強制したり、Filmの制作物をCoreの必須項目にしたりしない。上の媒体別の段階は境界を検査するための例であり、Templateの確定仕様ではない。全体の制作循環は[Creation Lifecycle](../vision/CREATION_LIFECYCLE.md)を参照する。

## 未決定の範囲

tOS v0.1全体の必須範囲と完成条件（OQ-01）は未決定のままである。本書の「Coreの最小境界」は責務を分けるための案であり、v0.1の実装範囲や完成宣言ではない。三層や交換点の実現性、実行環境、API、Automation、TemplateとProjectの生成・運用は後続の判断と検証を要する。
