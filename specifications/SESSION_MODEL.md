# tOS — Session Model

状態：B-06としてHuman Review承認済み（[PR #14](https://github.com/tanakakeisuke-github/tOS/pull/14)）。[Work Model](WORK_MODEL.md)と[Knowledge Architecture](KNOWLEDGE_ARCHITECTURE.md)を入力とする。

本書は短命なAI Sessionから長寿命のTaskを継続するための情報と境界を定める。Taskの状態・Human Gateは[Work Model](WORK_MODEL.md)、知識の正本・版・承認状態は[Knowledge Architecture](KNOWLEDGE_ARCHITECTURE.md)に従う。Sessionの開始や再開はTaskのReady承認、成果の引き渡しはDone承認を意味しない。

## Sessionと担当の原則

**一つの実行Issueを原則一人のFresh Workerが担当する。** Freshとは、担当Taskに指定された入力から目的・範囲・受入条件・停止点を読み直して着手し、前の会話の記憶を承認済み根拠として使わない状態をいう。一つのSessionで成果と自己確認まで進められる粒度を目安とするが、中断後に新しいSessionへ渡す場合もIssueの目的や承認状態は引き継ぐ。Session数や担当者の変更だけで新しいTaskを作ったり、既存のHuman Gateを省いたりしない。

成果のReviewは、作成を担当したWorkerとは別のReviewerが、Issueの受入条件と指定入力・成果・確認結果を独立に照合することを原則とする。Reviewerは別のSessionで開始し、Workerの説明だけを根拠にしない。継続Worker、担当交代、同一担当によるReviewなど原則からの例外が必要なら、担当IssueまたはReviewに理由、対象範囲、引き継ぐ入力と承認、独立確認への影響、判断した人間と時点を記録する。例外記録はReady・Done承認や必要な検証の代用にならない。例外の可否や範囲が既存承認と食い違うときは、影響する作業を止めて人間に判断を求める。

## 開始・終了・中断・再開

| 場面 | 確認・残す情報 |
|---|---|
| **開始** | 担当Issue、基準版、目的・範囲・受入条件・依存・停止点、指定された入力とその出所・承認状態、Ready承認の対象・範囲・記録先を確認する。Workerは理解した作業境界と不足・矛盾をIssueに照らす。ReviewerはReview対象の成果・確認結果と独立確認の観点も確認する。 |
| **終了** | 実施した作業、成果物の所在と版、受入条件ごとの確認結果と未実施の検証、判断・失敗・Unknown、残作業、Reviewまたは次の判断点を担当IssueまたはReviewから辿れるように残す。完了を自己宣言しない。 |
| **中断** | 中断時点の状態、変更した成果の版、済んだことと未着手のこと、停止理由、影響範囲、必要な判断者、再開条件を記録する。入力不足・矛盾・承認範囲外の判断があれば影響する作業をBlockedとして止める。 |
| **再開** | 新しいSessionは開始情報と中断記録を現行の適用版・承認記録に照合し、成果の状態と残作業を確認する。目的・範囲・入力・受入条件が変わるならWork ModelのReady前Human Gateへ戻す。矛盾や承認の曖昧さで停止した場合は、本文が変わらなくても人間の解決判断とその記録、適用版を確認してから再開する。その他の停止理由も解消と適用版を確認できた範囲から進める。 |

担当IssueをTask条件・状態・停止点・引き継ぎ情報への入口とし、成果とReviewの根拠はReview記録から辿れるようにする。判断理由と承認記録の正本はDecisionごとに担当IssueまたはReviewの**一方**を指定し、他方から参照する。新しい規則の正本は所有する仕様に置く。Outcomeには実施条件・観察結果・未検証点を残し、失敗の原因仮説と採用済み対策を区別する。Unknownには問い、影響範囲、判断者、関連する版・出典、次の判断点を付ける。Session内の会話だけにこれらを残さない。

入力の欠落、版や承認状態の不明、資料間の矛盾を見つけたときは、影響する作業を止め、担当IssueまたはReviewに箇所・版・影響・解決案と再開条件を記す。未解決でも当該作業を妨げない問いはUnknownとして保持する。推測で承認や仕様改訂を補わない。

## 中断から新しいSessionへの引き継ぎ例（架空）

「試作品の一つの操作について評価項目を整理する」Issueが、入力版A、評価項目一覧の作成、確認観点を範囲として人間のReady承認を得たとする。Workerは一覧の草案を作ったが、指定された測定条件が資料間で食い違うため、評価値の確定を止めた。中断記録には、IssueとReady承認の所在・対象版A、草案の版、完了した項目、未確認の測定条件、食い違う双方の出典、影響する評価値、判断者と再開条件を残す。追加の画面改修案は承認範囲外の提案として分ける。

新しいSessionのWorkerはIssue、草案、承認記録と食い違いの記録を読み、承認されたScopeを説明できるか照合する。測定条件の判断が未了なら評価値の確定は再開しない。人間の判断と適用版が記録され、元のScope内で進められると確認できれば、残りの評価項目を作る。判断が入力や受入条件を変えた場合はReady前Human Gateへ戻す。別SessionのReviewerは草案・最終成果・未実施の検証を独立に確認し、人間のDone承認までIssueを完了扱いしない。

## 検証前の仮説と将来構想

[Findings](../bootstrap/FINDINGS.md)のF-01・F-02・F-05には、長いChatや引き継ぎへの懸念・経験と、限定した入力やFresh Workerで誤解を減らせるかという**未検証の仮説**がある。会話長との因果、改善量、最適なTask粒度、引き継ぎ負荷、独立Reviewを含む総コストは未検証とする。本書の例も運用効果の実証ではない。比較や引き継ぎ試験の結果は条件とともにOutcomeに残し、採用する変更だけをHuman Review後に仕様へ反映する。

Context CompilerはTaskごとの入力・参照・承認状態をContext Packageへまとめる**将来構想**である。自動生成、優先度や承認の判定、品質保証、実装時期はここで定めない。本書の開始・再開時の照合は、担当者が指定入力と記録を確認するための条件である。
